# AI Token-客户需求测算与选型方法论

[[AI Token 业务]]知识库模块 21，是销售必修、售前与解决方案的核心工具，也是业务智能体的计算逻辑来源。解决三个串联的问题：客户到底要烧多少 token、该用什么模型、自建和买 API 各要多少钱。三段拆开回答就没有价值——客户真正在问的是"我这件事要花多少钱，有没有更省的做法"。能把这三段算清楚，我们才是顾问；只能报价，就只是通道。全模块贯穿一条纪律：所有测算都要给区间和假设，不给点估计，报精确数字客户会当承诺，偏差过大就会失去信任。

## 问题一：token 需求量怎么算

客户已在使用、有历史账单的，不靠估算靠读数据，重点是拆结构而非看总量：按输入/输出/缓存拆（找缓存命中率低但有大量重复前缀的立即可兑现的优化点，参考 [[AI Token-行业与Token经济]] 的缓存价格常识）、按模型拆（找"旗舰模型干简单活"的浪费）、按业务功能拆（通常符合 80/20）、按时段拆（波峰波谷比决定并发保障需求与自建划算与否）。

客户还没上线或要上新功能的，需要自下而上估算：月 token 量 = 月业务量 × 每次调用轮次 × 每轮平均 token（输入输出缓存分别算）。难点集中在"轮次"上，不同场景可以相差两个数量级，模块内提供了一张场景系数参考表（单轮问答、RAG 问答、长文档摘要、内容生成、工作流、Agent 循环、编程 Agent 等），用于快速定档而非承诺值。

其中最重要的一点是：Agent 场景的天真估算（轮次×单轮输入）会严重低估消耗，因为每一轮的输入都累积着前面所有轮次的内容。设初始上下文 C₀、每轮新增 ΔC、共 N 轮，总输入 token 约为 N·C₀ + ΔC·N(N-1)/2，第二项随轮次呈平方增长——这是等差数列求和，也是 [[AI Token-编程Agent]] 和 Agent 类场景烧钱的数学本质。一个 N=20、C₀=8000、ΔC=1500 的算例显示天真估算会低估 2.8 倍，轮次翻倍到 40 轮时消耗会涨到 3.3 倍而非 2 倍。这段推导建议原样讲给客户听，既证明我们懂技术，又解释账单为何超预期，还能自然引出上下文压缩和缓存的价值。

估算方法按精度排序：类比法（拿存量客户实际数据外推，±30%，我们客户数据越多越准，这是模块提到的"数据资产"具体形态）、自下而上（±50%，Agent 场景更差）、压测法（POC 跑真实流量按比例外推，±15%，客户愿配合时最优）。由于低估的代价（客户账单超预期、愤怒流失）远大于高估的代价（少赚一点），对客沟通一律用区间上沿，内部规划用中位数，并按场景设安全系数（确定性场景×1.3、工作流×1.5、Agent×2.0）。销售现场建议按序问七个问题定档，其中"能否提供一周真实账单"价值最大，能验证前六个问题的答案。

## 问题二：什么模型最合适

选型目标是在满足能力门槛的前提下最小化单位任务成本，而不是选最强或最便宜的模型。核心公式是：单位任务成本 = 模型单价 × 单任务 token 量 × (1 + 重试率)。弱模型往往在后两项同时吃亏——需要更多轮次、更高重试率——所以单价便宜的模型总成本完全可能更高，这也印证了 [[AI Token-行业与Token经济]] 中"低价模型往往更贵"的判断。这个公式的价值在于把"不推荐最便宜的模型"从"想多赚钱"变成"帮客户算总账"。

模块给出按任务层级配模型的矩阵：L1（分类、抽取、格式化，走量层 0.3–0.8 元档，越便宜越好）、L2（常规问答摘要翻译，主力层 2–5 元档）、L3（复杂推理、代码生成、Agent 规划，旗舰层 5–15 元档，这里省不得）、L4（多模态，按模态选专门厂商）。一个典型 Agent 业务跨三层配置后，成本通常能降到全程用旗舰的三到五成而效果几乎无损——这正是混合路由的设计依据，也是相对客户直连官方的核心价值（一个 Key、一套协议、账单可按层级拆开，对比直连官方要开多账号写多套适配）。

非功能约束是一票否决项：上下文长度、协议兼容（Anthropic 原生还是 OpenAI 兼容）、function calling/结构化输出稳定性、并发限流、合规备案（参见 [[AI Token-合规与风险控制]]）、多模态能力、缓存支持及计费方式。任何选型建议都应有评测支撑而非凭感觉：抽 30–50 条真实样本、人工标注期望输出、跑 2-3 个候选模型，比较准确率、单任务 token 量、单任务成本三项——后两项最容易被忽略却最具决定性。

## 问题三：自建还是买 API

决定性变量不是硬件价格,是 GPU 利用率。公开成本核算研究给出的关键临界点是自建相对 API 更划算的利用率约 52%（95% 置信区间 48%–56%），而典型 AI 创业公司的实际利用率只有 30%–50%，API 厂商集群利用率能做到 90%以上（靠聚合海量客户的波峰波谷互相填平）——也就是说绝大多数企业恰好落在临界点以下的"陷阱区间"，以为自建省钱实际更贵。

客户自算自建成本时通常只算 GPU 采购/租赁折旧一项，容易遗漏电力、带宽、机房托管、运维人力、模型迭代跟进、峰值冗余浪费、资金占用机会成本等项，其中运维人力常是最大也最常被遗漏的一项（参考量级中接近折旧的六成）。核心公式：自建每百万 token 成本 = 月总成本 ÷（理论月产能 × 实际利用率），最常见的测算错误就是用理论产能而非实际产出做分母，会让自建成本看起来低 2–3 倍——网上流传的"自建比 API 便宜 5–100 倍"多是只算电费、未计折旧运维、未按利用率折算所致，遇到客户拿这类材料来可直接指出分母问题。盈亏平衡点 Q\* = 自建月固定成本 ÷ API 单价，实际算例中往往远超绝大多数企业客户的量级，一算出来自建话题基本就结束。

这个 52% 利用率临界点与 [[AI Token-梁文锋520投资讲话精华]] 中流出材料所称的"上游按十个月回本定价、让独立部署第三方无利可图"是同一件事的两个独立视角——上游靠极高集群利用率压低单位成本再合理定价，天然挤压了自建的经济空间（注意对外只能引用 52% 这组公开数据，不能引用梁文锋材料中未经证实的表述）。

但客户选择自建也可能不是为了省钱——数据不出域、不受限流、深度定制、内部立项需要、长期战略考量，这些理由用成本反驳无效且会暴露我们只想卖 token。正确姿态是承认理由成立、转向混合架构：常规负载走本地零边际成本，复杂任务走外部模型，两边账单合并成一张统一视图——这也是 [[AI Token-外部观点收录与研判]] 中应对"自建推理替代 API 采购"风险的现实答案。同时也应诚实承认：当客户月消耗稳定超过盈亏平衡点、负载平稳利用率能维持 60%以上、有专职运维、模型选型固定、且有明确合规或定制刚需时，自建确实更优，硬推 API 并不专业，但这类客户往往仍需要一条 API 通道做峰值溢出补充。

## 标准测算流程

把三段串成售前流程：问量（七个问题定档，能拿到真实账单直接读数据）→拆层（内部把业务拆成 L1–L4，识别浪费点）→出选型建议（30–50 条样本跑评测）→算三笔账（当前方案、优化后方案、自建方案）→出报告（《成本分析与优化建议报告》，销售流程中最重要的交付物，必须写明测算假设与主要不确定性来源）。模块还建议把需求测算器、选型对比器、自建对比器三套公式做进业务管理台工具化。
