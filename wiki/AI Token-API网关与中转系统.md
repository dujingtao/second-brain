# AI Token-API网关与中转系统

[[AI Token 业务]]（SpaceTiD）内部知识库模块 14，覆盖 New API、One API、LiteLLM 三个开源项目，是 [[AI Token-客户端技术知识库总纲]] 第五层的详细展开。数据采集日 2026-07-27。原始模块含一节内部专用的自研网关选型判断（标注"对外分发需删减"），因本页是内部知识库，予以保留。

这一层比较特殊：它既是客户可能在用的东西，也是公司自己业务的本体。当客户说"我们自己搭了 New API"，这句话包含三层信息——他已经在管理多个模型渠道（用量到了一定规模）、他有技术能力自建基础设施（技术型团队）、他此刻正在寻找上游渠道（公司可能是他的供应商之一）。这是最优质的线索类型之一：不需要教育他"为什么要多模型"，他已经在做了，只需要一条稳定、便宜、能开票的上游通道，销售周期极短。同时，公司自己的网关（见 [[AI Token-供给体系与产品架构]]）也在和这些开源方案竞争，客户随时可能问"我为什么不自己搭一个 New API"，这个问题答不好单子就没了。

## New API

由 QuantumNous 开发的开源 AI 模型管理与分发系统，基于 One API 二次开发，把各家大模型的官方调用结构统一转换成标准化调用格式，2025 年 10 月约 11k+ Star，是目前中文社区最主流的自建网关方案。定位不只是协议转换器，而是一套完整的 AI 资产管理系统——有用户体系、渠道体系、令牌体系、计费体系和可视化控制台。

核心能力：多模型聚合与格式互转，原生支持 OpenAI、Claude Messages、Gemini 三种格式并可互转（这一"原生支持"正是行业普遍缺失的痛点，New API 在这方面做得比多数简易中转站好）；缓存计费支持（可配置缓存计费倍率，0-1 区间，说明自建 New API 的客户已具备缓存意识，谈缓存优化不能停留在扫盲层面）；企业级管理（令牌分组、模型限制、差异化用户配置，四级权限体系：公开访问、用户令牌、管理员令牌、Root 访问令牌）；可视化控制台内置统计与性能监控。关键配置项：流式超时默认 300 秒、Gemini 最大图片数默认 16、最大文件下载 20MB。

部署要求 Linux 环境（社区推荐 Ubuntu 24.04）+ Docker，通过 docker-compose 部署，默认端口 3000，需配套 MySQL/PostgreSQL 和 Redis。真实评估：对有运维能力的团队不难，半天能跑起来，但"跑起来"和"跑得稳"之间差距很大——高并发下的连接池调优、数据库性能、渠道健康检查、故障自动切换都要自己趟，这是公司与自建方案竞争的主战场。

**成为其上游**：客户在 New API 后台走"渠道管理→新建渠道"，类型选 OpenAI（或对应协议），代理地址填 `https://api.域名/v1`，密钥填公司签发的 Key，模型列表填公司支持的模型 ID。技术支持要重点提醒三件事：模型 ID 必须与控制台一致（New API 支持"模型重定向"映射内部名，不用重定向就必须一字不差，这是接入失败头号原因）；争取配成"高优先级渠道"而非"备用渠道"（很多客户接进来就忘了调优先级，量一直上不去还以为是客户不认可）；倍率配置要对齐（分组倍率、模型倍率配错会导致客户成本核算与账单对不上，首次接入最好由技术支持陪同配置一遍）。

用量画像：自建 New API 的客户用量已过自助阶段，通常是要给内部多团队分发 Key 的 AI 应用公司、做二次分销的小型中转商、做统一管控的企业 IT 部门，月消耗通常在千万到十亿 token，波动可预测性较好。两个典型诉求：采购价要低（他们自己也在算差价）、通道要稳（对下游有承诺）——价格敏感度高于平均，但稳定后粘性也很高（切换上游要重新配置和验证）。

三个销售切入点：做主力上游（直接目标，谈判重点是价格和 SLA，客户都懂产品价值不用多讲）；做冗余通道（拿不下主渠道就先进备用位，New API 支持自动故障转移，只要公司够稳，主渠道波动时流量会自然流过来，是低阻力的进入方式）；说服从自建转向托管（最难但价值最高，核心论点不是"你搭得不好"，而是自建出问题时的三件事——上游波动谁去切、账单对不上谁去查、开票和备案材料找谁要——这些人力成本客户是否算过）。诚实的边界：客户团队有专职运维、用量很大、对成本极度敏感，自建对他确实是更优解，这种情况下硬推托管是徒劳的，应老实做他的上游渠道。

## One API

New API 的上游项目，也是整个中文 LLM 网关生态的源头，定位相近——统一管理与分发主流 AI 模型 API。与 New API 的关系：New API 在其基础上二次开发、功能更多迭代更活跃，One API 更轻量更稳定但新特性跟进较慢，市面还有 MIXAPI 等衍生分支，基本都源自这一脉。

对客户的选择差异：需求简单、只要基础多渠道分发与 Key 管理、追求稳定不折腾的团队更适合 One API；需要缓存计费、多协议原生转换、更细分组倍率与用户体系的团队更适合 New API。对公司而言两者几乎没有差别——接入方式完全一致（渠道管理→新建渠道→填 base_url 和 Key），技术支持不需要准备两套文档，只需注意版本差异导致的界面路径不同，做接入指引时问清楚客户用的是哪个、什么版本。

## LiteLLM

与前两者定位完全不同，是一个 Python 库，让开发者用极少代码改动在 100 多个模型之间切换。流传很广的比喻："LiteLLM 是开发者的瑞士军刀，New API 是企业的瑞士银行"——前者在代码层面解决模型接入问题，后者在运维层面解决基础设施管理问题。也提供 Proxy Server 模式（可当网关跑），但核心心智仍是"库"，主要用户是写代码的人不是管平台的人。

用 LiteLLM 的客户通常处于更早阶段——可能是独立开发者或还在写 MVP 的创业团队，用量小但技术判断力强、迭代快、成长性好。接入方式：在配置中把公司注册为 OpenAI 兼容 provider，填 `api_base` 和 `api_key`，对开发者是几分钟的事。

销售策略与 New API 客户完全不同：不用"稳定性、SLA、发票"那套企业话术，他现在不关心这些，关心的是模型全不全、有没有免费额度试、文档清不清楚、出问题能不能在社区快速问到人。应该用"开发者关系"的方式服务而非销售的方式——给测试额度、写好文档、在技术社区保持存在感。今天月消费 200 元，一年后产品跑起来可能就是月消费 20 万。

## 横向对比

| 维度 | New API | One API | LiteLLM |
|---|---|---|---|
| 形态 | 完整管理平台 | 完整管理平台 | Python 库+可选 Proxy |
| 主要用户 | 团队/生产环境 | 团队/轻量场景 | 个人开发者/早期项目 |
| 协议支持 | OpenAI/Claude/Gemini 原生 | 以 OpenAI 为主 | 100+ 模型抽象 |
| 计费与多租户 | 强（分组倍率、令牌体系） | 中 | 弱（非核心能力） |
| 缓存计费 | 支持（可配倍率） | 有限 | 依赖上游 |
| 部署复杂度 | 中（Docker+DB+Redis） | 中 | 低（pip 安装） |
| 公司的角色 | 上游渠道 | 上游渠道 | 上游 provider |
| 客户价值 | 高、粘性强 | 高 | 低但成长性好 |
| 服务方式 | 商务+技术陪同 | 同左 | 开发者关系 |

## 对自研网关选型的启示（内部）

研究透这一层最大的收获不是竞品分析，而是明确自研网关必须在哪些地方超过开源方案——因为客户随时可以自建，必须回答"凭什么用你的而不是自己搭"。

开源方案已做得很好、不必也不该纠缠的：多渠道分发、Key 管理、基础倍率计费、可视化控制台，这些是及格线，做到即可，不构成差异化。

开源方案的公认短板，即公司的机会点：
- **企业级保活与故障转移的成熟度**：开源网关普遍缺乏企业级保活机制，上游波动时表现不稳定，这是 SLA 承诺的立足点。
- **账单颗粒度与成本归因**：开源方案能算钱但算不清"哪个业务、哪个功能、哪个时段最烧钱"，这正是分析层与 [[AI Token-定价体系与单位经济模型]] 的用武之地，也是从工具走向服务的唯一路径。
- **合规配套**：开源网关不会帮客户准备模型备案文件、公示材料、6 个月日志留存的导出能力，这是自建方案永远补不上的一块（见 [[AI Token-合规与风险控制]]），也是攻克企业客户的钥匙。
- **优化建议的能力**：开源方案给数据，公司给结论——"这个月有 62% 的输入是重复前缀，做缓存能省 1.8 万"这句话开源网关说不出来。

给决策层的判断：不要试图在功能数量上和开源方案竞争，那是一场必输的消耗战。护城河只能建在"运维确定性+成本管理能力+合规配套"这三件开源社区没有动力去做的事情上，这与 [[AI Token-商业模式与价值主张]] 里的护城河判断完全一致。
