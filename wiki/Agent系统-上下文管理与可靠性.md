# Agent系统：上下文管理与可靠性

对应 [[Claude Certified Architect认证-总览]] 的 Domain 5（占比15%，5个Task Statement，虽然占比最小但和其他4个Domain的很多考点交叉）。

## 上下文窗口管理

**Lost in the Middle 效应**：LLM对长输入的**开头和结尾**关注度高，中间内容容易被忽略/漏掉，即使中间的信息直接回答了问题。解法：把关键发现摘要放在最前面（利用首因效应），加section headers帮助导航中间内容；不要指望靠切换更大context窗口的模型解决——这不是容量问题，是注意力质量问题。

**长对话摘要丢失关键细节**：摘要本身就是有损压缩，数值、百分比、日期在渐进式摘要（progressive summarization）中容易被模糊化成"大约""差不多""一些"这种说法。解法：把关键事实（金额、日期、订单号、政策引用）提取到一个**持久化的"case facts"块**里，这个块**不参与**摘要过程，每一轮都原样注入prompt。

**上游输出过大**：子agent输出总量太大（比如155K tokens）但下游agent处理最优区间是50K tokens左右 → 解法是让上游agent**只返回结构化关键信息**（事实+引用+相关性评分），从源头减少token消耗；**不要**加一个中间摘要agent去压缩——这只是多了一层处理，治标不治本，正确方向是从源头减少，而不是后处理压缩。

**上下文预算约束（子agent层面）**：每个子agent应该在有限的上下文预算内工作，只拿到完成任务所需的最少信息；指示子agent返回结构化结果而非原始数据转储；用 `allowedTools` 限制子agent工具集——工具越少，干扰越少，上下文成本也越低。

**结构化传递格式**：内容和元数据要分离——内容层是事实、发现、引用；元数据层是source URL、文档名、页码、相关性评分。这样既保留了引用归属，又方便下游按需筛选。

## 升级决策（Escalation）

什么时候该升级给人工：
- **政策空白**——没有规则可以遵循，agent不能自己编造规则去套用（比如"竞品比我们便宜30%，能不能给折扣"，而政策只覆盖自家网站降价的情况）
- **需要主观判断**——超出agent能力范围，需要同理心判断
- **不可逆的高风险操作**——需要人工确认
- **超出agent权限**——比如退款金额超过agent的授权上限（这种应该优先用hook强制，而不是仅指望升级判断）
- 客户**明确要求**"找人工"——应该立即升级，不要先尝试自己解决

什么时候**不该**升级：
- 有标准流程可循的情况（比如物流争议有明确的处理流程）
- 客户一条消息里有多个问题（agent有能力拆解并逐一处理，不是升级的理由）
- 猜测"客户可能会改主意"不是升级理由

**处理情绪但不代表要升级**：客户表达不满（"这太离谱了！"）时，正确流程是先**承认情绪**，再**提出具体解决方案**，只有当客户**再次坚持**要找人工时才升级——客户第一次表达不满不等于要求转人工。

**多匹配结果消歧义**：工具返回多个匹配结果（比如按姓名搜到多个客户）→ **不要**凭启发式规则（比如挑最近下单的那个）去猜 → 应该向用户请求额外的标识信息（邮箱、电话、订单号），因为用户对自己的身份有确定性的了解，多一轮对话的成本远低于选错账户的代价。

**升级 vs 程序保障的核心区分**：
- 升级（escalation）= 需要人的**判断**（没有规则可循的情况）
- 程序保障（hook/前置条件）= 有规则、但需要**100%执行**（退款上限、身份验证顺序）

判断路径：后果是否涉及金钱/安全？→ 是 → 程序级保障（不是升级，是硬限制）；有没有政策覆盖这个情况？→ 没有（政策空白）→ 升级；有标准流程 → 不升级，agent自己处理。

不可靠的升级触发方式（都不对）：情绪/sentiment分析（客户情绪和case复杂度不相关）；模型自评置信度1-10分（模型可能自信地判断错误，校准很差）；单独训练一个分类器（过度工程化，且往往缺训练数据）。

## 优雅降级与部分失败处理

**核心区分（必考）**：
- **"0 results"**（查询成功执行了，只是没有匹配项）→ 这是**有意义的空结果**
- **"timeout"**（查询根本没跑完）→ 这是**失败**，需要决定是否重试

**绝对不能做的**：默默跳过不上报（silent skip）——把失败伪装成"没有匹配"的成功返回，会让coordinator误判，藏错误 = 最终输出有缺口但没人知道。

正确做法：
- 部分数据源失败 → 用已经拿到的数据继续合成，而不是中止整个任务
- 在最终输出里**明确标注覆盖范围**：哪些领域有充分数据、哪些有缺口、哪些数据源直接失败了（比如报告里用"FULL COVERAGE"/"PARTIAL COVERAGE — search agent timeout"这种小节标注）
- 数据冲突（两个可信来源给出不同数字）→ **保留两个值 + 标注冲突**（`conflict_detected: true`），让coordinator决定怎么处理，子agent自己**不要**擅自选一个当"更可能正确"的答案然后完成分析

结构化的子agent错误应该包含：失败类型（`failure_type`）、尝试过的查询（`attempted_query`）、部分结果（`partial_results`）、可能的替代方案（`alternative_approaches`）、这次失败对整体覆盖范围的影响（`coverage_impact`）——这些信息让coordinator能做出"重试/换个查询/用部分结果继续/换个子agent"这类明智的恢复决策，而不是只给一个模糊的"search unavailable"。

## 保留来源（Provenance）

多源信息合成时，"claim → source"的映射关系很容易在摘要化过程中丢失。正确做法：每条结论都保留 `source_url`、`source_name`、`publication_date`、`confidence` 这类归属信息。

**处理冲突数据**：两个来源给出不同数字时，不要靠"可信度启发式"武断选一个当正确答案然后只在脚注提一句差异；也不要让下游agent在不知情的情况下自己选。正确做法是把两个值都保留、显式标注为冲突（`conflict_detected: true`），附上可能的原因（比如方法论不同、统计时间点不同），交给有更全局视角的coordinator去决定怎么协调。

**日期标注避免误判为矛盾**：没有日期信息时，两个不同时间点的数据容易被误读成"矛盾"，实际上可能只是"随时间增长"。所以合成时要带上发布/采集日期。

**按内容类型渲染**：不要把所有内容都塞进同一种格式——财务数据用表格、新闻和分析用叙述性文字、技术发现用结构化列表、时间序列按时间顺序排列。

## 置信度校准与人工审核

字段级置信度分数：让模型对每个提取字段输出置信度 → 低置信度优先人工审查；但**高置信度也可能有错**，所以还要做**分层随机抽样**（每个置信度分组都抽一部分去核实），因为一个97%的**整体**准确率可能掩盖了某个特定文档类型/字段40%的错误率——按文档类型和字段维度拆开分析准确率，而不是只看汇总指标。

速记：**低置信优先审，高置信也要抽**。
