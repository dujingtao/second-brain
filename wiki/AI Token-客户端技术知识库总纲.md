# AI Token-客户端技术知识库总纲

[[AI Token 业务]]（SpaceTiD）内部知识库模块 12，是客户端技术知识库（模块 12-17）的总纲和索引。数据采集日 2026-07-27，开源项目迭代极快，版本号与 Star 数以最新官方仓库为准。

## 为什么要建这个库

客户买回 token 不是拿着发呆，要把 API Key 填进某个具体的东西里——可能是桌面聊天客户端、IDE 里的编程插件、服务器上的自托管 Agent，也可能是企业内部的应用编排平台。"填进去的东西"决定三件对公司至关重要的事：

1. **决定 token 怎么烧**：桌面客户端一个月消耗几百万 token，多 Agent 循环调用的编程助手一天能烧几千万，同样是一个客户，接入形态不同收入量级差两三个数量级。不了解客户用什么就无法做容量规划和授信判断。
2. **决定技术支持成本**：客户接不上来时，问题九成不在网关而在工具的配置方式（base_url 末尾要不要加 /v1、模型 ID 要不要带厂商前缀、走哪种协议）。技术支持不懂这些工具，每个接入问题都要来回三五轮，这些工时直接吃掉贡献毛利（见 [[AI Token-定价体系与单位经济模型]] 的服务强度）。
3. **决定销售能不能对上话**：客户说"我们在用 Cline"，销售能立刻接上"token 消耗应该主要在长上下文重传，试过缓存系统提示词吗"，对话性质就完全不同——懂客户的工具是从"卖 token 的"变成"懂行的人"最快的路径。

一句话定位：这不是技术文档搬运，是**把技术信息翻译成业务信号**，每个项目都要回答"它是什么"和"它对我们意味着什么"，后者更重要。

## 技术地图：五个层次

客户侧 AI 技术栈分五层，理解分层就能在客户报出工具名时立刻定位它在哪一层、大概什么量级、该问什么问题。从第一层到第四层，客单价、决策复杂度、服务成本、粘性全部递增，销售资源应优先投向第三、四层，第一层靠自助，第二层靠内容和口碑。

1. **桌面客户端**（Cherry Studio、ChatBox、LobeChat、Open WebUI）：个人或小团队的对话入口，最接近消费级，用量小笔数多，几乎不需要人工服务，是长尾客户主要形态。详见 [[AI Token-桌面客户端]]。
2. **编程 Agent**（Claude Code、Cursor、Cline、Roo Code）：跑在 IDE 或终端里为写代码服务，是当下 token 消耗最猛、最不可预测、最容易失控的层——Uber 四个月烧光全年预算的案例就出自这一层。详见 [[AI Token-编程Agent]]。
3. **自托管 Agent 与助手**（Hermes Agent、OpenClaw、OpenManus）：跑在服务器上、有持久记忆、能自主执行任务，特点是长期在线+定时任务+多轮自我循环，消耗曲线持续而非脉冲。详见 [[AI Token-自托管Agent与通用助手]]。
4. **应用编排平台**（Dify、Coze、FastGPT、n8n、RAGFlow）：企业搭建自己 AI 应用的底座，一个平台可能挂几十个业务流程，是企业客户主要形态，单客户量大、决策链长、粘性高。详见 [[AI Token-应用编排平台]]。
5. **API 网关与中转**（New API、One API、LiteLLM）：比较特殊，既是客户可能用的东西，也是公司自己的业务本体——客户如果自建了 New API，说明已经在做多模型管理，公司要么成为其上游渠道之一，要么说服其用托管服务替代自建。详见 [[AI Token-API网关与中转系统]]。

## 三种接入协议

几乎所有客户端工具接入网关都走这三种协议之一，技术支持必须能在 30 秒内判断客户用的是哪一种，因为 base_url 写法完全不同：

- **OpenAI 兼容协议**（最通用）：绝大多数工具默认选项，base_url 通常填到 `/v1` 结尾。调用非 OpenAI 模型时模型 ID 往往需要带厂商前缀（如 `anthropic/claude-...`、`deepseek/deepseek-v4`），前缀写法各家网关不一致，是接入失败的头号原因，文档必须把自己的写法写死写清楚。
- **Anthropic 原生协议**：Claude Code、Cline 的 Anthropic 模式使用，base_url 通常不带 `/v1` 而指向专门的 Anthropic 端点，认证头也不同（`x-api-key` 而非 `Authorization: Bearer`）。原生支持这个协议是区别于低端中转站的关键能力——靠中间件转译会丢字段，导致 tool use 行为异常。
- **Gemini 原生协议**：使用面较窄，部分多模态场景需要。

销售话术：三种协议都原生支持、不做中间件转译，很多中转站只支持 OpenAI 协议，用 Claude Code 或需要 function calling 时会出各种莫名其妙的问题。

## 通用配置速查与高频报错

技术支持第一页纸，客户报出工具名直接照表回答（Claude Code 走 Anthropic 原生 `https://api.域名/anthropic`，其余多数工具走 OpenAI 兼容 `https://api.域名/v1`）。三个高频报错的标准答复：

- **401 Unauthorized**：Key 错了，或用错了协议对应的认证头，先确认协议选对没有。
- **404 Not Found**：十有八九是 base_url 结尾的 `/v1` 多了或少了（OpenAI 协议要有，Anthropic 端点不要）。
- **模型不存在**：模型 ID 写法不对，多半是厂商前缀问题，让客户从控制台模型列表直接复制。

## 按接入形态预判用量

这是销售做容量规划和授信判断的依据（数量级是经验区间不是承诺值）：桌面客户端个人级十万到百万 token/月、纯预付不给账期；编程 Agent 单人千万到亿级、波动剧烈单日可翻十倍、需预付+强制预算熔断；自托管 Agent 常驻千万到亿级、持续型；应用编排平台企业级千万到十亿级、可预测性较好可给账期。

**最重要的判断规则**：凡涉及 Agent 循环调用的形态（编程 Agent、自托管 Agent），必须在开户时就把预算上限和熔断规则配好，不能等客户自己想起来——这类客户第一张账单如果超预期三倍，流失概率极高，而这本来可以避免。

## 维护规则

开源项目迭代速度远超商业软件：Star 数、版本号、具体配置项按季度复核（配置路径变更会导致技术支持给出错误指引，伤害专业形象）；新工具出现先记录再补全（客户提到不认识的工具，当天先登记名称和客户描述，一周内补全档案）；每次技术支持解决新的接入问题，把解法补进对应项目的配置章节（支持工单是这个库最好的素材来源）。
