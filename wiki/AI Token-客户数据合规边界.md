# AI Token-客户数据合规边界

[[AI Token 业务]]知识库模块 26，起因是一个具体问题：能不能用客户授权的对话记录去微调模型，从而提升 AI 反应速度和准确性。答案是"能，但你想做的那件事不能做，而真正能做的那件事不需要动模型权重"。这个模块本身的结论重要，但过程中意外撞见的另一个发现更重要，直接关系到公司整条业务线是否合法存在——放在本页最前面说。

## 最重要的发现：转售必须先拿书面授权，否则业务线本身违约

核查上游数据条款时发现，**阿里云百炼、腾讯混元、智谱三家的服务协议都明确禁止未经书面许可的转售**：

- 阿里云百炼第 4.6 条："未经我们及相关权利人书面许可，您不得转售本服务及平台内模型"。
- 腾讯混元第 2.6(6) 条："未经腾讯云事先书面同意，不得通过出租、出借、出售、分销、转售或转让等其他方式向第三方提供本服务或本服务的 **API Token**"——原文点名 "API Token"，没有解释空间。
- 智谱用户协议七条 3 款、GLM Coding Plan 团队套餐协议六条 2 款："不得将 GLM Coding Plan 以转售、代售、转包装、**聚合转发**等方式向任何第三方提供"，也不得共享账号让他人实际使用——"聚合转发"四个字目前是唯一直接以我们这种业态为规制对象的措辞。

结论：如果只是拿标准商用账号去转卖阿里/腾讯/智谱的额度，**在协议层面已经构成违约**，厂商可依约随时终止，且参照同类条款通行做法，可能不退未消耗余额。

但三家条款的措辞都是"未经……书面许可/同意"，这不是禁止业态，是要求逐案授权。唯一可行路径是走各家的官方渠道/经销/ISV 合作，签订书面转售授权。这意味着**官方代理资质从"锦上添花的信任背书"变成了"业务合法性的前提"**——[[AI Token-渠道与代理商体系]]和批发分销这两条业务线，没有书面授权在协议上是站不住的，这是一个定性的变化，不是风险管理的量的调整。

进一步的结构性困境：**协议允许转售的厂商，数据条款往往差；数据条款好的厂商，恰恰明确禁止转售**。腾讯混元默认不用输入训练（4.2 条承诺），但转售限制最严格，点名 API Token；智谱通用 API 默认允许用于训练（用户协议四条 10 款"匿名数据机器学习/模型算法训练"），且转售限制里点名了"聚合转发"；Kimi 数据条款最差（默认授权用于"模型服务优化"，无关闭开关），但转售限制反而最宽松（仅要求"供内部使用或向最终用户提供服务"）。也就是说，条款干净和拿货自由这两件事没法同时占到。

与国内厂商相比，OpenAI、Anthropic 都明确不默认用 API 数据训练、留存期可数化、可申请零数据留存（ZDR）。国内**没有一家厂商提供 ZDR**，这是结构性的——国内的留存要求本身就是为了配合监管溯源，与 ZDR 直接冲突，这个差距补不了，只能如实向客户说明。

立即行动项：盘点当前每一家已接入/计划接入的上游账号类型是否被协议允许用于转售；把书面转售授权的商务谈判作为业务合法性前提去推进，而不是可选项；签约时索取"渠道协议里的数据处理附录"（这份文件公开检索不到）；核实火山方舟、百度千帆的协议正文（两家文档站为 SPA，未公开可抓取，若火山"永久授权且技术上不可撤回"属实，影响重大）。

## 客户对话数据能不能用于提升模型：结论

回到最初的问题本身。整个论证拆成三句话：

1. **不要用客户对话去微调模型**——不是因为不合规（虽然确实很难合规），而是因为它解决不了问题。客户抱怨的"不准"绝大多数是事实性错误，而学术证据（Ovadia 等，EMNLP 2024）显示微调在注入新事实知识上收益极弱、甚至为负：Llama2-7B 在全新知识任务上微调后准确率从 0.353 掉到 0.219，同一任务 RAG 是 0.585。微调擅长教格式、教风格、教任务范式，不擅长教事实，而客户的痛点恰恰主要是事实性的。花一个数量级的钱换一个可能更差的模型，还背上一个客户能举证、自己无法自证的法律敞口，不划算。
2. **绝对不做跨客户数据混用**——这是本模块唯一的红线级禁令，同时踩三条线：法律上无法履行 PIPL 第 23 条的告知义务（接收方名单动态且不可枚举）、商业上侵犯客户商业秘密、技术上有可举证的泄露路径（对微调模型的成员推理攻击 AUC 已达 0.938，见下文）。
3. 真正能提升速度和准确性的三条路径完全不需要读客户对话内容：上游 prompt caching 对齐（缓存读价降到 0.1 倍，是合同写死的确定性收益）、网关自身链路优化（唯一 100% 由自己掌控的延迟）、精确缓存（哈希级匹配，不需要理解内容）。

一句话版本：把"数据 → 模型权重"这条路封死，把"数据 → 评测集 / 示例库 / 路由策略"这条路做深。前者是幻觉，后者才是护城河。

## 法律枢纽：不是"有没有授权"，而是"我们的法律身份会不会翻转"

大多数人把这个问题想成"客户授权了没有"，这是错的。真正决定合规性的，是每种用法下我们的法律身份会不会从 PIPL 第 21 条的"受托处理者"翻转成第 23 条的"独立个人信息处理者"。受托处理者只是按客户指令干活，不需要终端用户单独同意；一旦被认定为自主决定处理目的和方式的独立处理者，就必须取得终端用户的单独同意并逐项告知我方名称、联系方式、处理目的等。这个身份判定**不以合同怎么写为准，以实际处理目的为准**——把跨客户知识库包装成"受客户委托构建"是无效的形式包装，因为本质是在为自己和其他客户的利益使用某个客户的数据。

另一个反直觉的点：客户企业无权替它的终端用户授权。合同相对方是客户企业，但对话记录里的个人信息主体是客户的终端用户。如果我们是受托处理者，客户的授权链条是有效的；但一旦我们要自主使用数据（微调、跨客户库），客户合同里"我保证已取得授权"只是一项民事担保，能让我们向客户追偿，但不能免除自己的行政责任——PIPL 第 66 条的责任是按各自处理者身份独立追究的。换句话说，客户签的那张纸在监管面前保护不了我们。

一份"概括授权"之所以不够，有四条独立理由（任何一条都足以否定）：合同相对方是企业而非个人信息主体；一揽子条款不满足"单独同意"要求的"专门、具体、明确"；终端用户在客户的 App 里根本不知道我方的存在，告知义务无法满足；把"同意用于训练"与"能否使用服务"捆绑属于被禁止的强迫同意。此外处理目的变更（从提供推理服务变为训练）依法需要重新取得同意。

这里也澄清两个常见的错误引用：一是《生成式人工智能服务管理暂行办法》第十一条常被误读为"禁止将用户输入用于训练"，其实原文只禁止"非法"留存/提供，"非法"二字把判断标准指回了 PIPL 本身；二是《网络安全法》"日志留存不少于六个月"针对的是网络运行日志，不能用来为"保留全量对话内容"做合规背书。

## 三种用法的合规判定：难度差着数量级

把"用客户数据"拆成三种用法，难度排序是跨客户共享 ≫ 单客户微调 > 单客户内缓存/检索。

**单客户内部的缓存、RAG、提示优化**——难度低，唯一可规模化落地的路径。数据不出客户边界、不改变处理目的，稳稳留在受托处理关系内。工程上要解决四点：委托合同写全六要素并保留处理记录 ≥3 年；严格的租户隔离（一旦 A 客户的缓存命中 B 客户的请求，性质立刻变成跨客户共享，这是架构上最容易"滑坡"的地方）；转委托给上游厂商需客户明确同意；合同终止后必须有可验证的删除机制。

**用客户对话做微调**——难度高，路径存在但成本极高，列出的十个卡点里最致命的一条是：相关国标（GB/T 45654-2025）要求提供便捷关闭选项（不超过 4 次点击到达）并显著告知，但作为中间层没有终端用户界面，这个义务只能靠客户侧实现而我们无法验证，也就是说这条用法的合规性永远建立在一个自己控制不了的环节上。

**跨客户共享的知识/示例库**——红线，不做。除了继承单客户微调的全部卡点，还叠加：向 A 客户的终端用户告知"接收方 B 是谁"这件事，在多租户网关上接收方名单动态且不可枚举，结构上不可能做到；客户 prompt 里的业务逻辑、代码命名是商业秘密，跨客户共享独立构成违约和不正当竞争风险，与个人信息问题无关，即便信息清理干净这条依然成立。唯一相对可行的改造，是不用原始对话，只沉淀经人工抽象、不含任何客户业务内容的通用方法论。

## 为什么"脱敏/匿名化"不是免责出口

PIPL 第 73 条把去标识化和匿名化分得很清楚：去标识化是"不借助额外信息无法识别特定自然人"，仍然是个人信息，全部义务继续适用；匿名化是"无法识别且不能复原"，才不再算个人信息。差别在可复原性——去标识化保留了钥匙，匿名化要求钥匙被销毁且不可能重建。

对话自由文本在实操上**做不到匿名化**，原因有四：准标识符不可穷举（"我在 XX 医院看的 XX 科"这类描述正则和 NER 无法保证召回）；稀有组合仍可重识别；模型记忆化会让"不能复原"的假设失效——去标识化语料进入训练后模型仍可能逐字复现；我们不掌握客户的业务上下文，无法评估重识别风险，而这恰恰是判断是否达到匿名化标准的前提。

因此纪律是：把"我们做了脱敏"定位为降低风险的安全措施，**绝不能作为免除同意义务的法律主张**。对外宣称"已匿名化因此无需同意"，在监管检查时是高风险陈述——这是这一模块要传达给对外沟通口径最关键的一条约束。

另外要注意，我们事先无法知道某条 prompt 是否含 PIPL 第 28 条定义的敏感个人信息（生物识别、宗教信仰、医疗健康、金融账户、行踪轨迹、未成年人信息等），所以不能按"分类型分别取同意"设计产品，只能要么全部按敏感信息标准处理，要么入库前强制过滤并接受残余风险。已检索范围内，中国境内目前没有以"未经单独同意将用户对话数据用于模型训练"为主要案由的公开处罚案例，但 2026-04-30 部署的"清朗·整治 AI 应用乱象"专项行动已把"训练中使用未经授权的数据"明文写入整治清单，风险窗口在收窄。

## 技术现实：即便合规问题解决了，这条路在技术上也是错的

这一节的证据不依赖法律解释，因此更有决定性。学术实验反复显示，微调在注入新事实知识上普遍弱于 RAG，甚至出现负收益（Llama2-7B 案例见上文）；LoRA 相比全参微调能显著减少"灾难性遗忘"，但目标域性能也随之打折扣，两者是取舍关系。真正划算的几条路径——上游 prompt caching 对齐、精确缓存、模型路由——全部不需要理解对话内容，且收益是合同或工程层面确定的，不依赖模型质量假设。对外宣传口径需要注意：模型路由的成本降幅在知识密集/推理密集任务上是 35%–45%，"85%"这个数字只在 MT Bench 这种偏闲聊的基准上成立，不要用来对客户宣传。

从成本结构看，训练本身很便宜（一次典型 LoRA 微调几百到几千元量级），真正的成本杀手是独占推理实例的托管——按公开价格测算，为一个微调后的模型做独占部署，打平所需的月调用量往往超过实例物理吞吐上限的数倍，即在物理上就不可能比直接调用同级 API 更便宜。这个结论与 [[AI Token-Token工厂可行性与起步路径]] 从财务倒推得到的"公有云 token 自建供给不成立"是两条独立路径互相印证的同一结论。

## 客户能举证，我们不能自证——这是本模块最不对称的风险

学术研究（Carlini 等，ICLR 2023）证明大模型存在可测量的记忆化：模型规模每增加 10 倍，可提取记忆比例显著上升；训练数据中重复出现的序列被逐字复现的概率远高于只出现一次的数据。而客户的系统提示词、模板、固定话术在日志里天然高频重复，正好落在"高重复=高可提取"的区间，这不是小概率事件，是结构性的。

更关键的是成员推理攻击：针对微调模型的 SPV-MIA 方法（NeurIPS 2024）平均 AUC 达到 0.938，意味着客户拿一段文本就能高置信度判断"这段是否在你的微调集里"。**客户有技术手段证明自己的数据进了我们的模型，我们没有任何技术手段证明它没进**——举证责任的不对称是结构性的，不是靠合同条款能平衡的。差分隐私也救不了这一点，因为它保护的是"某条样本是否参与训练"，而客户合同关心的是"你有没有拿我的数据训练"，这是目的限制问题，DP 不提供豁免。

另一个值得记住的区分：真实发生过的跨租户数据泄露事故（如 OpenAI 2023 年 3 月的 redis 连接状态污染事故，泄露了部分用户的聊天标题和账单信息）发生在**网关/缓存层**，不是模型训练层——目前没有检索到模型训练导致跨企业客户数据吐出的公开确认案例。这对我们的工程启示是：真正该优先防的是租户隔离做错的共享缓存，缓存键必须包含租户 ID，并建立跨租户命中的自动化检测告警，这是不可豁免的技术评审项。行业内也没有一家主流网关厂商在做"跨客户数据微调"，主流形态是日志 → 数据集 → 动态 few-shot/评测集，权重不变、数据可按租户删除和审计，这是更应该抄的形态。

## 可执行的分级方案（L0-L4）

把"用客户数据"拆成五个等级，逐级放行，不得跳级：

- **L0**：上游 prompt caching 对齐、网关链路优化、精确缓存（含租户 ID）。完全不需要数据内容，法律身份仍是受托处理者，标准委托合同即可。**立即做，优先级最高。**
- **L1**：模型路由（仅用长度、任务类型等元数据，不读内容）、用量与成本可观测性。同样是受托处理者身份，标准委托合同覆盖。**可以做。**
- **L2**：单租户内的 RAG、示例库、提示优化、评测集，数据严格不出客户边界、不进模型权重、单条可删。前提是隔离到位，合同要写全委托六要素并配合事前个人信息保护影响评估（PIA）和可验证删除机制。**可以做，但架构必须先过隔离评审。**
- **L2.5**：单租户语义缓存。需谨慎——误命中会实际损害回答准确率（研究显示 2.7%–7.5% 的命中是错的），且必须有跨租户命中告警。
- **L3**：用单个客户的数据微调仅供该客户使用的模型。数据进入模型权重，法律身份翻转为独立处理者，需要终端用户单独同意、授权记录、大模型备案、语料安全评估。**暂不做**——经济性不成立（打平点远高于物理吞吐上限），且合规链条有结构性断点（无法验证客户侧是否真的提供了合规的关闭开关）。重新评估需同时满足三个条件：客户明确提出需求且愿自行完成终端用户单独同意；客户流量能把一个小规模实例压到高利用率或提供覆盖固定成本的付费承诺；在其数据上做过对照实验，证明微调相对"RAG+提示优化"有可复现的显著增益（这一条最容易被忽略，不能因为客户愿意付钱就跳过验证）。
- **L4**：跨客户数据混用（共享库或混合微调）。法律身份是独立处理者且构成向第三方提供，告知义务在结构上无法履行。**红线，永不做。**

三条红线需要反复强调：不做跨客户数据混用（包括"匿名化后"的共享示例库）；不把"我们做了脱敏"作为免除同意义务的法律主张；未通过租户隔离评审前不上线任何共享缓存组件。

## 对外怎么说

当客户问"你们会不会用我的数据"，这是一次销售机会而不是防守场景，因为国内上游厂商在这件事上的条款普遍很差，我们可以做得比上游更干净。推荐的话术结构是：明确说明只做转发、计费、可观测性三件事；把"不用数据训练"从道德承诺转化为架构事实（架构里根本没有这条通路，比"承诺不做"更有说服力）；把能提供的优化归因到缓存折扣、模型路由降本、租户内评测集沉淀这三个真实来源；顺势提示"国内主流大模型平台里有几家的默认条款允许用输入优化模型且没有关闭开关"，帮客户把流量路由到条款干净的厂商——这也是 [[AI Token-商业模式与价值主张]] 里场景化解决方案线的自然延伸。

## 对既有结论的修正：数据本身不是有效的粘性资产

一个直觉判断是"持有客户数据能增加粘性、对抗[[大模型厂商]]的脱媒"，本模块否定了这个直觉的一半：模型权重不是有效的粘性资产，因为经济性不成立（独占部署打平点高于物理吞吐上限），且客户可以举证追责（成员推理 AUC 0.938），一旦被举证，粘性会瞬间反转成法律负债。真正有粘性的是评测集、路由策略、成本基线、可观测性数据——它们随客户业务演进而增值，迁移时需要重建，且完全在委托处理关系内没有法律敞口。修正后的表述是：对抗脱媒的资产不是"我们拥有客户的数据"，而是"客户在我们这里积累了他自己都还没来得及沉淀的运营知识"，前者是占有、后者是共建，后者的粘性更强因为它不引发对抗。这与 [[AI Token-商业模式与价值主张]] 中场景化解决方案线"从替客户建改成让客户自己建的东西跑得更省"的定位是同一个结论从两条独立路径（行业主张、合规与技术分析）分别得出的。
