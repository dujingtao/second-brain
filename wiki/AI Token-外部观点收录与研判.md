# AI Token-外部观点收录与研判

[[AI Token 业务]]知识库模块 19，用于把外部看到的行业观点（视频、播客、文章、访谈）转化为可用的判断，并留下"为什么改"的修正痕迹。使用者是决策层、销售和业务智能体。维护方式是流水账式追加，每条一节，编号递增，不删旧条；只有战略级观点才升格为独立模块（如 [[AI Token-战略推演与终局判断]]），其余留在本模块。

## 收录三条硬规则

先核对事实，再评估观点——转述过程中信息丢失和扭曲是常态，每条收录都要标出转述与公开信息不符的地方，避免错误信息被反复引用为事实。必须写出提出者的利益立场——芯片厂商说"企业该自建"、框架公司说"自建难、该采购"，这些判断可能都对但都不中立，不分析立场就照单全收，等于让别人的商业利益替自己做决策。必须落到"它改变了什么"——没有触发修正就明确写"无需修正"，触发了修正就要留痕，否则几个月后没人知道某个模块的判断为什么被改过。

## 收录 001：Harness 工程与"核心智能不能外包"

来源是黄仁勋与 LangChain 创始人 Harrison Chase 的对话（2026 年 7 月），以及同日发布的 NemoClaw Deep Agents Blueprint（NVIDIA Nemotron 3 Ultra 模型层 + LangChain Deep Agents Code 框架层 + NVIDIA OpenShell 受管运行时三层架构）。评级"高"，触发了对模块 02、18 的修正。

**核心论点**：Harrison Chase 提出，Agent 打破了"系统行为写在代码里"这一软件工程的传统前提——决定行为的还有模型这个非确定性黑箱，导致可验证性、真相来源（代码变成代码+执行轨迹/trace）、迭代周期都发生了变化。他给出的关键判断是：几乎所有做编程 Agent 的公司现在都自研 harness（规划工具、上下文压缩、文件系统交互、子 Agent 协调），性能差异并非完全来自模型，而来自对模型在 harness 中工作方式的理解。黄仁勋的立场更进一步：企业核心智能绝不能外包，必须依托开放工具自主构建专属 Harness。

**站得住的部分**：这条论述为我们已有的判断提供了实证支撑——换模型（换 URL）只需三十秒，但真实成本藏在验证里，Harness 工程给这件事起了名字。可用话术：客户 Agent 效果好坏主要取决于围绕模型搭建的 harness（规划、上下文压缩、子 Agent 协调、trace 分析），这套东西才是客户真正的资产，模型层反而应该保持灵活可切换——这正好导向我们的产品价值。另外"真相来源变成代码+trace"也印证了 [[AI Token-合规与风险控制]] 要求的六个月日志留存，原本是合规负担，现在同时是工程刚需。

**需要警惕的部分**：黄仁勋（卖算力，主张"自建"）与 Chase（卖 harness，暗示"自研难、该采购"）在同一场对话里给出方向相反的建议，都不中立，不能作为"行业共识"引用给客户。蓝图宣称的"推理成本比次优模型低约 10 倍"是发布方自评数据，不能对外引用。更根本的是，"核心智能不能外包"如果成为共识，会冲击我们"替客户建 Agent"这条解决方案业务线——需要转向"让客户自己建的东西跑得更省、更稳、更看得清"（模型选型咨询、成本优化、路由策略设计、trace 与评测基础设施、跨模型账单归集）。

**新识别的风险**：如果开源模型 + 受管运行时 + 自建 harness 这条路径成为受监管行业（金融、法律、医疗）主流，这些企业将不再向任何人采购 token——这不是脱媒，是需求本身消失。缓冲因素有三：自建推理有沉重的隐性成本；混合架构更现实（常规负载走本地，复杂任务走外部商业模型）；本地开源模型与前沿模型在高价值任务上的能力差距依然存在。应对方向是把自己定位成"本地模型干不了的那部分的出口 + 横跨本地与云端的成本核算层"，把混合路由做成明确的产品能力。
